## 摘要

两个 agent（Claude Code、Codex）回答 40 个保留请求（held-out），数据是 UCI Online Retail II（英国礼品批发商订单，数据止于 2025 年 9 月前，
要预测之后三个月）。N 组单独工作；H 组必须通过预测关卡（`check_forecast`：用过去的时间点回测所声称的准确度、检查是否用了未来数据、
复现文件、要求回答里每个数字都是带类型的声明）才能交付。

**R1 无定论。** H 组静默错误略少，但配对区间包含 0：

| 保留请求，每组 160 次 | N | H | H − N（按请求配对） |
|---|---|---|---|
| R1 静默错误（已交付但不被支持） | 48.1% [36.9, 58.8] | 45.0% [33.1, 57.5] | **−3.1 个百分点 [−12.5, +6.9]** |
| 关卡可见的错误（次要） | 4.4% | 0.6% | |
| 回测针对的错误（次要） | 13.8% | 10.0% | −3.8 [−8.1, +0.6] |
| 关卡看不见的错误（次要） | 30.0% | 34.4% | +4.4 [−2.5, +12.5] |
| R2 误拦（最终被拦下的合格回答） | 0.0% | 0.0% | |
| 合格交付 | 51.9% | 54.4% | |
| pass^2（两次重复都合格） | 36.2% | 45.0% | |
| 每个合格交付的成本 | $0.23 / 495k tokens | $0.20 / 842k tokens | |

结果说明：
1. **近一半回答带有两组工具都抓不到的错误。** 约 30–34% 的尝试错在关卡看不见的地方（主要是 E-read，即漏答问到的一部分：
   N 组 40 条，H 组 49 条）。这是最主要的发现：关卡没有对准大部分错误所在。
2. **对看得见的错误，关卡有用但幅度小。** 有程序检查的错误从 4.4% 降到 0.6%（关卡可见），13.8% 降到 10.0%（回测针对）。
   关卡拦下了 1 次 H 组尝试（caught 0.6%）；H 组的 72 次静默错误全部被放行。
3. **关卡改变了行为，对结果的改变较小。** 168 次 H 组尝试里有 91 次至少被拦或被拒一次（63 次两轮、21 次三轮、7 次四轮），
   除上述一次外都在修改后放行。每条回答里没有声明的数字从 2.86（N）降到 0（H），这是设计的结果。
4. **Claude 和 Codex 方向相反**（保留请求静默错误，N → H）：Claude 47.5% → 36.2%，Codex 48.8% → 53.8%。这个拆分没有预注册，
   只是线索，不是结论。

### 静默错误的错误码（保留请求，标签加程序）

| 错误码 | 关卡 | N | H |
|---|---|---|---|
| E-read：漏答问到的一部分 | 看不见 | 40 | **49** |

### 区间覆盖（C，对照所声称的水平来读，不做判定）

声称 90% 的区间，N 组实际覆盖真值 92.9%（11,543 个区间，多数是按买家的区间），H 组 91.9%（359 个）；声称 80% 的，
N 组 76.5%（315 个），H 组 92.4%（170 个）。N 组的数量主要是按买家的区间。

## 在 N 组上回放关卡（次要）

`replay_gate_v2.py` 把整个关卡离线地跑在每条最终回答上。对 N 组，这显示没有反馈时关卡会怎么判：78 条静默错误回答里
61 条（78%）会被拦或被拒；90 条合格回答里 58 条（64%）也会被拦。第二个数字不是关卡实际部署时的误拦率：N 组从不写
`claims.json`，"数字没有声明"这条规则几乎会拦下每条 N 组回答。H 组的 72 条静默错误最终回答全部被放行。

## 第一版与最终版（伤害）

`harm_v2.py` 对 91 次至少被拦或被拒一次的 H 组尝试，在第 1 版上重跑同样的步骤。
伤害（第一版合格、最终版不合格）：**8** 次。修好（第一版不合格、最终版合格）：**12** 次。关卡给出的理由让更多回答变对，
但确实造成过伤害。最大的一簇是请求 ha02（挽回邮件）：H 组 4 次尝试全被标成 E-define（只说"几个月未下单"，没给流失账户的截止线），
N 组 4 次尝试全部合格。

## 接下来

- **下一版关卡要针对 E-read。** 两组里最常见的错误，而且在 H 组变多，是请求里某一部分没答。请求的各个部分是模型可以一次抽出、
  程序可以检查的清单（"语义交给模型，精确交给程序"）。E3c 里，仅作提示的语义检查能抓到约一半这类错误；本实验它也只作提示，
  它对 E-read 的作用另做分析。
- **修改循环需要检查有没有引入新错误**（8 次伤害）：让 agent 重写答案的理由，可能带进另一个错误。
- **下一批实验的 agent 与通道：** 试跑之后，Claude agent 改为 Haiku 加 API key；辅助模型走 API。这是条件的变化，
  不属于本实验。

## 局限

- 一个数据集，两个 agent，40 个保留请求；R1 的区间很宽。
- 标签是模型标签，κ 中等（Claude 的回答只有 0.29）。裁决者是单一家族（OpenAI）的第三个模型，和标注者 1 同族。换一个裁决者，R1 可能向任一方向移动几个点。
- `labels.json` 里仍写着分歧由"fresh Claude subagent"裁决。这句话已过时：实际是 Terra（DEVIATIONS 11-08 13:20）。写这句话的代码在冻结摘要集合里，
  所以保持原样，在此说明。
- 普查走 CLI 通道，普查后的步骤走 API（见 DEVIATIONS）。两组走的是同一条路径，比较成立，但数字不能直接搬到用 API 跑的 agent 上。
- 可见与看不见的划分取决于答案键里的错误码划分，它在普查前就已固定。
