## 0. 一页结论

1. **不要再做"AI 数据科学团队"。**
   - 生成 SQL、dbt、pipeline、模型代码的能力已经商品化。Snowflake CoWork/CoCo、Databricks Genie Code、BigQuery 数据工程/数据科学 Agent、阿里云 DataWorks Data Agent、dbt Wizard 都已 GA 或公测〔E-5.1–5.22〕。
   - "一个 Supervisor 加十几个固定角色"的架构，在紧耦合、需要单写者的数据工作上成本高、收益不明〔E-6.15, E-6.16〕。

2. **要做的是一层薄的"可验证交付层"（DS Harness）。** 它由四类自建资产组成，全部以代码形式存在 git 里：
   - ① **上下文资产**：语义层/指标定义、认证表、verified queries、Agent Skills、AGENTS.md；
   - ② **确定性验证与 CI 门禁**；
   - ③ **Agent 评测集**；
   - ④ **价值账本**。

   Agent loop、NL2SQL、数仓、调度器、目录、模型注册表、沙箱、LLM 网关一律复用或购买。
   任何 Agent，不论是平台原生的、Claude Code / Codex，还是境内 Qwen / DeepSeek 栈，都通过 MCP 工具和 Skills 接入，产出**带证据的数据产品**。

3. **为什么是这一层：瓶颈在语义和验证，不在生成。**
   - dbt 的小样本测试（11 题 × 20 次）中，建模 schema 加上语义层后问数准确率 98–100%（不加为 84–90%）；在私有企业仓库基准 BEAVER 上，SOTA agent 只有 10.8%（给 oracle 提示后 30.1%）。两者不是同一基准；独立测得的语义层增益约 +8~25pp〔E-4.4, E-4.11〕。
   - 语义层更大的作用是把"看起来对的错答案"变成明确的"答不了"〔E-4.11〕。
   - 静默错误是主要失败形态：在一篇论文（RADAR）对 DS-STAR 基线的测试中，零分运行里 69.8% 是看似正常的错答，没有报错，只是数错了〔E-4.13〕。
   - 自我反思、多 agent 辩论都消除不了静默错误。辩论的收益基本等于投票〔E-4.16〕；不跑代码的 LLM judge 最高也只有约 82% 的准确率〔E-4.14〕。

4. **先做什么。** 在同一个有财务关账的业务域（例如收入/订阅）里，同时推进两条工作流：
   - **W1 数据管道断修/变更**：oracle 是 CI 加精确对账，成本低，可以先挣得自治；
   - **W2 认证指标问数**：用语义层加 golden set，可以先挣得采纳。

   ML 放在第二波，以"决策 + 随机实验"交付，不以 AUC 作为交付物。

5. **没有金标准怎么办：主动构造 oracle，不假设它已经存在。** 按强度排列：
   - 与独立记录对账（财务关账、支付结算、源系统控制总数）；
   - 不变量和变形关系；
   - 双路径复算；
   - golden set；
   - 延迟真值回溯评分；
   - 随机抽检；
   - 随机实验；
   - 缺陷注入。

   每一种只在自己的适用范围内算证据（§5.1）。

6. **怎么判定"能用"：一条证据阶梯、一套用户标签、一个门禁。**
   - 证据阶梯 V0–V5；
   - 用户信任标签 T0–T3；
   - 门禁三态 ALLOW / HOLD / REJECT。
     - 缺失、过期、出错、证据不足 → HOLD；
     - 只有经过认证的 FAIL → REJECT；
     - Agent 自己写不出 PASS。

   没有标签的数字不得进入 KPI、董事会材料或对外报告。

7. **价值只认三条可审计的渠道：**
   - ① 已核验正确的基线需求 × 净节省工时 × 兑现系数 κ（默认 0.3）；
   - ② 被替代的外部支出；
   - ③ 随机实验证明的决策增量（取 95% 置信下界）。

   裁员、DAU、自报的"省了几小时"都不算 ROI。

   按 §2.4 的全成本时薪和 7.1 的汇率假设，中国 IT 人员的人力成本约为美国的 1/8–1/4〔E-8.19, E-8.20〕，所以在中国只算省工时，常常是负值。中国侧的价值要落在决策速度、单人覆盖规模、收入类 KPI 和外包替代上。

8. **中国侧：境内栈是默认，不是对照组。**
   - 默认执行器用 DataWorks Data Agent，或 Qwen Code 配 Qwen / DeepSeek / GLM。
   - 个人信息和重要数据只走境内模型。向境外模型 API 发送含个人信息的 prompt 即构成出境〔E-2.13〕。
   - 不向境内公众提供服务的企业内部工具，通常不需要生成式 AI 备案；面向公众时才需要〔E-2.9〕。

9. **参考实现已经跑通，并量出了机制效果【实测】。**
   - `dsharness` 包含：合成订阅公司（9 类植入缺陷、已知真值、随机化挽留项目）、受治理管道、语义层、3 个角色的 MCP 工具、验证库、门禁、封存评估、uplift 学习与实验读数、基准；共 444 个测试。
   - 脚本化基准共 38 项，其中 29 项用了错误方法、28 项结果确实错误：不加 harness 时，这 28 项全部以"成功"交付；加上 harness 后，**静默交付为 0**。代价是 3 项正确结果没有自动交付：2 项转人审，1 项按设计 HOLD。
   - 决策闭环如实给出了不讨喜的结论：
     - 按风险联系客户，真实价值是 −1.69 元/人；naive 方法却声称 +19.84 元/人。
     - uplift 策略的真实价值是 +0.78 元/人，但一个月的实验只能给出 INCONCLUSIVE。
     - 系统因此 HOLD 扩量；预跑功效分析给出 MDE（约 15–18 元/人），并指出按历史实测价值，加样本也不太可能 PASS；固定每月打 500 个电话，无论怎么选人都亏损，被拦下。
   - 详见 §9。

10. **证伪条件写在前面（§10.2）。** 例如：在你自己公司的 golden set 上，语义层的增益如果低于 8pp，或者平台原生 agent 与本方案相差不到 3pp 而成本更低，就应该收缩自建范围，只保留资产、评测和账本。

## 1. 问题的重新表述

### 1.1 你提出的四个难点：成立，但还缺第五个

你提出的四个难点是：①数据正确吗；②处理和使用方法正确吗；③模型可靠吗；④能投产并带来价值吗。这四个都成立。

还需要补上第五个：**⑤ 每个结论有没有与其用途相匹配的证据。**

这五种"正确"相互独立，不能互相替代：

| 层 | 问题 | 典型失败 | 主要 oracle |
|---|---|---|---|
| 计算正确 | 代码有没有按定义计算 | 去重口径错、JOIN 扩行、单位错 | 不变量、双路径复算、对账 |
| 语义正确 | 定义是不是业务真正的意思 | "净收入"是否含退款、是否排除测试账号 | 语义层加 owner 签字、口径委员会 |
| 统计有效 | 推断是否成立 | 泄漏、切分错、窥探 holdout | 封存评估、时间穿越检查 |
| 因果有效 | 行动是否真的有效 | 把相关当因果、按风险排序当按价值排序 | 随机实验 |
| 商业有用 | 是否改变了决策并产生净收益 | AUC 提升但利润下降 | 实验读数 + 价值账本 |

### 1.2 关于"缺少金标准"和"让多个 agent 辩论"

**缺少金标准，是数据科学的常态。** 出路不是去找一个万能的验证模型，而是在每个环节构造便宜的 oracle，并把每条结论能用到什么程度限定在它拿到的证据之内。

企业其实手里已经有不少"免费的金标准"，只是很少被系统地用起来：
- 财务关账数；
- 支付渠道结算单；
- 源系统的控制总数；
- 已经发布的看板；
- 会延迟到来的真实结果，比如 30 天后客户是否真的流失。

**多 agent 辩论或评审团不应作为正确性的判据。** 理由有三条：
- 辩论在数学上是一个鞅，收益主要来自投票〔E-4.16〕；
- 同源的模型会犯相关的错，4 票一致不等于 4 份独立证据；
- LLM judge 的判断会随答案顺序波动最多 14%〔E-4.14〕。

评审团可以留在三个位置：
- 对高价值的单题，生成 N 个候选，按执行结果选择；
- 用干净上下文的 reviewer 审 PR，要求它只输出可执行的探针，并且探针在 CI 中真的让候选失败才算数；
- 评叙述质量，用成对比较，随机化顺序，并对照人工标注做过校准。

任何评审团如果要默认开启，必须先在同等预算的消融实验中证明自己的价值（ADR-10）。

## 2. 价值与经济模型

### 2.1 用例组合

排序依据是"可度量价值 × 可验证性 × 可行性"。所有 KPI 都必须与审计正确率配对报告。

| # | 工作流 | 主 KPI | oracle | 现实可行性证据 | 自治：起点 → 12 个月上限 | 优先级 |
|---|---|---|---|---|---|---|
| W1 | **DE 断修/变更**：schema drift 适配、失败任务分诊、dbt/SQL 变更、按既有模式新建模型、回填计划 | MTTR、数据停摆时长、无大改合并率、30 天回滚率、逃逸缺陷数 | CI 测试、data-diff、精确对账 | 抽取和加载约 96%；**构建**转换 23–33%，pass^3 比 pass@1 低 8–16pt〔E-4.8〕；数据层问题必须真的去查数据才能修〔E-4.9〕；OpenAI 用 Codex 迁移约 1 万个 DAG〔E-3.3〕，Grab 有 Scarlet〔E-3.12〕 | L2 → L3（仅非生产） | P0 |
| W2 | **认证指标问数/取数** | 自助解决率、机械工单占比、首答时间 | 语义定义、verified query、延迟真值回溯 | 语义层带来 +8~25pp〔E-4.11〕；Grab 的 SQL 自助解决率从 50% 升到 81%，机械工单占比从 44% 降到 30%〔E-3.12〕 | 回答提问者 L1；进入共享看板需挣得 L3 | P0（以过盈亏线为前提） |
| W3 | 数据质量与对账监控、分诊 | 消费前拦截数、定位时长、误报率 | 对账、不变量 | 确定性检查即可 | L1 → L2 | P1 |
| W4 | A/B 读数 Skill | 读数周期、被拦下的功效或 SRM 错误数 | 确定性统计库 | 快手 `/abtestSkill`〔E-3.15〕 | L2 → L3（仅内部报告） | P1 |
| W5 | 替代外包的报表、数据运营、标注 | 财务确认的已终止合同金额 | 合同 | 替代外部支出是最清晰的 ROI 来源〔E-8.3〕 | 视任务而定 | P1（有外包时） |
| W6 | **决策模型工厂**：留存 uplift、需求预测、定价 | G6 实验 ITT 增量毛利的 95% 置信下界 | 封存 holdout、随机实验 | MLE-bench 获牌率 61–64%〔E-4.6〕；但按风险排序 ≠ 按价值排序 | 训练 L2；晋级永远由人决定 | P2 |
| W7 | 开放式归因与因果问题 | 决策时效 | 多数没有 | 交互式歧义任务只有 8.67–17%〔E-4.4〕；超出能力前沿时，人的正确率从 84.5% 跌到 60–70.6%〔E-8.12〕 | L1：作为**假设工厂**，产出可证伪的假设而不是结论（§4.1） | P1 |

**首年不做**：
- 在信贷、核保、雇佣等高风险决策中让 LLM 做决定；
- 自研通用 NL2SQL 引擎；
- notebook copilot；
- 开放网页抓取（受《网络数据安全管理条例》约束〔E-2.11〕）。

### 2.2 价值公式

```
NV_月 = Σ_w κ·N_w^base·a_w·(t0_w − t_r,w)·c_h       ① 只计原本会进人工队列、现在被分流的基线需求
      + V_ext                                         ② 财务确认的已终止外部合同
      + Σ_m LCB95(ΔKPI_m)·u_m                          ③ 只计通过 G6 的实验增量，取 95% 置信下界
      − Σ_w N_w·a_w·ε_w^UB·L_w                         ④ 已交付错误的期望损失
      − (C_llm + C_compute + C_review + C_curation + C_platform_eng + C_build摊销 + C_vendor)

CPVC（每个经核验正确任务的成本）= 总成本 / (N × 审计正确率)
```

**参数规则**：

- **a**：经抽审判定正确的接受率。
- **t0**：用 2 周时间-动作法，或 IM 登记机器人计时测得，不用自报。
- **κ**：默认 0.3。只有发生现金事件（合同终止、招聘需求撤回、积压实测下降）并经财务确认后，才取 1。
- **ε^UB**：随机抽审得到的 95% 上界。
- **L**：取自事故台账。
- **诱发需求**不计价值：Ramp 的 agent 频道 4 周收到 1,476 个问题，原求助频道只有 66 个〔E-3.13〕。新诱发的需求只有挂到某条决策记录上才计价值。

### 2.3 成本结构

结论先行：**在试点规模下，token 一般只占总拥有成本的 10–15% 以下【假设】。主要成本是上下文策展和人工复核。** 因此设计目标是压低"每个被接受的产出需要多少分钟人工复核"。

| 任务 | token【假设】 | 海外中档模型 | 境内模型 | 主要成本 |
|---|---|---|---|---|
| 认证问答 | 60k 输入（缓存命中 70%）+ 3k 输出（参照 Vercel d0 每题约 61k〔E-3.4〕） | Sonnet 5.5（$2/$10，缓存读 0.05×）约 $0.07；新 tokenizer 约 +30%，计入后约 $0.09〔E-8.16〕 | DeepSeek V4-Pro 闲时约 $0.02；flash 约 $0.005〔E-8.17〕 | 5% 抽审，每次约 5 分钟 |
| DE 断修 PR | 0.5–3M | $1–5，用 `--max-budget-usd` 封顶 | $0.5–3 | 人工复核 15–30 分钟，加克隆环境的 CI 计算 |
| 一轮模型候选 | 0.5–2M，另加训练算力 | $1–10 | — | DS 复核 1–2 小时 |

**三个需要提前防范的成本坑**：

1. **2026 年境内在涨价。** DeepSeek 8 月上调 50%–1,100%，并出现过约 12 小时宕机；智谱和各家云的算力也在涨价〔E-8.18〕。DeepSeek 的峰时（UTC 01–04、06–10）正好落在北京时间的工作时段。所以交互式问数只能付峰价，富化和评测一律在闲时批量跑。
2. **平台促销会到期。** Databricks Genie 对用户免费到 2027-01-31，但 service principal（也就是自动化流程）的调用现在就计费〔E-5.7〕。Google data agents 试用结束后约为每百万 data token $3/$20〔E-5.12〕。预算一律按促销结束后的价格做。
3. **仓库扫描费。** Agent 生成的探索性 SQL 会产生扫描费用，比如 MaxCompute 按扫描量计费、Snowflake 按仓库 credit 计费。工具层必须做 dry-run 成本估算、按人和按 agent 的配额，以及分区裁剪 lint。

### 2.4 盈亏平衡（全部为【假设】，用于决定"建还是买"）

**通用参数**：
- 接受率 a=0.5，单件节省时间 Δt=35 分钟。
- 首域固定成本按 1.75 FTE 计：steward 0.5、eval 0.25、平台工程 0.5、建设摊销 0.5。这是首域分摊的份额：§6.3 的平台工程（1–1.5 FTE）和 eval（0.5 FTE）是团队总投入，在多个域之间分摊；只有一个域时，N* 要相应上调约 40–70%。
- 后续每个域按 0.75 FTE 计。

| 口径 | 全成本时薪 | 首域盈亏点 N*（κ=0.3 / 0.5） | 后续域 N* |
|---|---|---|---|
| 美国 | $95（$120,230 ÷ 0.70 ÷ 1,800h）〔E-8.19〕 | 约 3,300 / 1,900 | 约 1,400 / 820 |
| 中国非私营 | ¥168（¥248,752 × 1.35 ÷ 2,000h）〔E-8.20〕 | 约 3,900 / 2,200 | 约 1,650 / 930 |
| 中国私营 | ¥87（¥128,166 × 1.35 ÷ 2,000h） | 约 4,400 / 2,300 | 约 1,900 / 1,000 |

N* 的单位是"可治理请求/月"。

由此得出三条规则：
- **每月可治理请求低于首域 N\* 时，不要自建 W2 的数据访问层。** 直接用平台原生问数（CoWork、Genie、DataWorks ChatBI），自己只持有 golden set、语义层和账本，同时让 W1 与 W2 分摊平台工程的成本。
- **在中国口径下，只算工时多半是负值。** 立项依据要换成决策速度、单人覆盖规模、收入 KPI 或外包替代。
- **只按基线需求计价值时，"省工时"的论证往往很薄。** 要么靠多个域分摊固定成本，要么叠加外部支出替代和决策价值。

dsharness 提供了一个可调参数的组合 ROI 计算器：`dsh roi --profile cn|us`，见 `economics/roi.py`，每个输入都标明了来源或"假设"。注意它的默认参数与本节不同（中国 ×1.4、年工时 2,000 小时，不含 κ），也不计算 N*；本节的 N* 为手算。

### 2.4.1 买还是建：与四类现成选择的对比

本方案不替代这四类选择。它叠在它们之上：无论买什么，这一层都要自己持有。

| 选择 | 典型产品 | 直接能给你的 | 给不了的 | 什么时候只买它就够 |

### 2.7 一个算得清的例子：决策价值从哪里来

在 dsharness 的合成世界中【实测，基于 custody 真值】，7 月初在册的 3,584 名活跃（非测试）客户构成当月的风险集，平均真实流失概率 4.9%：

| 分群 | 人数 | 对挽留的反应 |
|---|---|---|
| persuadable（可说服） | 1,130 | 有效 |
| unmoved（无反应） | 2,064 | 无效 |
| sleeping dog（会被打扰到） | 390 | 联系后反而更容易流失 |

每月联系 500 人。下表是不同渠道、不同选人方式下的月度期望净价值：

| 渠道与成本（折扣只给留下的人） | 按**真实**流失概率选前 500（oracle） | 按**真实** uplift 选前 500（oracle） | 按真实期望价值选前 500（oracle） | 实验功效（每组 250 人；价值 LCB95>0 / 仅"流失下降"ITT） |
|---|---|---|---|---|
| 电话：每次 ¥15 + 20% 折扣 | **−¥8,199** | −¥5,844 | −¥5,722 | — |
| App 消息：每次 ¥0.5 + 10% 折扣 | ¥1,602 | **¥3,999** | ¥4,003 | 按风险 0.06 / 0.23；按 uplift 0.37 / 0.87 |

注意：这张表用的是**真值**排序，是"知道答案时"的上限。用学到的流失模型选人（§9.3），真值是 −1.69 元/人。

从中可以读出三条结论：

1. **渠道经济学决定能不能做。** 在这个世界里，只要每月固定打 500 个电话，无论怎么选人都会亏钱；即使有完美模型，也只有 46 人值得打（每月约 +¥764）。一个诚实的系统应该拦住它，而不是把"流失少了几个人"当成功劳。
2. **选人方式决定赚多少。** 如果**知道真实 uplift**（oracle），按 uplift 选人的价值约是按风险选人的 2.5 倍。按风险选人会大量选中无反应（unmoved）的客户（真值排序的前 500 人中有 316 人，学到的模型选出 346 人），sleeping dog 只占少数（0 人 / 13 人），这正是 Ascarza (2018) 讲的 "Retention Futility"〔E-1.23〕。但 uplift 要从有限的实验数据里**学**出来。§9.5 的实测显示：
   - 学得出多少，取决于数据采集（有没有采集能反映价格敏感度的信号）和规模；
   - 中等规模企业的单月实验，往往只能给出 INCONCLUSIVE。
3. **好的选人方式让实验更容易下结论，但门槛比想象中高。** 同样 500 人（每组 250 人），"流失下降"的 ITT 检验功效从 0.23 提高到 0.87；但门禁要求的是扣除成本后价值 LCB95>0，它的功效只从 0.06 提高到 0.37。要达到 80% 的价值功效，真值 uplift 名单每组约需 743 人，风险名单每组约需 9,900 人。所以单月实验多半仍是 INCONCLUSIVE（§5.6）。

这些数字放大到真实规模后，比如 100 万订阅用户，就是每月数十万元量级的差别【假设：线性外推】。

更重要的是，这笔钱只有走完下面这个闭环才拿得到：历史随机化项目 → 学习 uplift → 预注册实验 → 读数 PASS → 扩量。只训练一个 AUC 很高的流失模型，拿不到这笔钱。§9 给出了参考实现在这个闭环上的实测结果。

**采集与标注细则**

- **源契约**必须写明以下内容：
  - 主键、更新时间、迟到窗口、重叠回看策略；
  - 删除和墓碑（tombstone）语义、写入模式。

  源级控制总数对账通过后，数据才发布为 READY。出现新 schema 时，先登记为候选版本，并阻断不兼容的下游（dsharness 的 D8 就是这种情况）。
- **埋点**：
  - 用事件规范 YAML 描述；
  - 每天把事件量与后端订单、支付记录对账；
  - agent 只能以 PR 的形式提出埋点改动。
- **非结构化数据**（合同、工单文本、通话转写）：LLM 抽取是管道算子，按代码管理。
  - 模型 ID、prompt 和输出 schema 一起计入 `pipeline_digest`。三者任一变更都算管道变更，必须走 `pipeline_merge`。
  - 抽取结果落表，保留 `extracted_at` 和 `extractor_digest`。PIT 特征的可得时间取 `max(原文 available_at, extracted_at)`。
  - 换模型或改 prompt 后重抽历史数据，按**回填**处理：提交计划 PR 和 dry-run diff，经双人审批，永不自动执行。
  - 新旧版本在 200 条人工金标上做配对比较：字段级的准确率（P）和召回率（R）都不下降，才允许合并；未达阈值的字段只能标 T3 使用。
  - 文本中含个人信息的，按 C2 路由。
  - 批量抽取在闲时执行，按条计入成本。
- **标签分四级**：confirmed、expert_adjudicated、weak、model_generated。人工队列分两条：
  - **随机或分层审计队列**：用于估计总体错误率，必须记录抽样概率；
  - **错误发现队列**：只用于找错，不能拿来估计总体错误率。

  金标要盲标，冲突要裁决，kappa ≥0.8。
- **合成数据**："AI+"政策鼓励使用〔E-8.23〕。但它只用于测试和基准，必须打上 synthetic 标记，永远不进入评测真值或价值核算。

- **外部数据**（数据交易所、合作方、公共数据授权运营、第三方标签）：
  - 接入前登记来源的合法性、授权用途和期限，以及能否用于训练、能否出境。这些用途字段写进 catalog，超出授权用途的查询由工具层拒绝。
  - 供应商会回溯修订历史数据。快照按到货日期保存，PIT 特征只使用当时已经到货的版本。
  - 续费前做增量价值测试：在同一个封存 holdout 或实验上，比较加入这个数据源前后的效果；没有增量就不续费。
  - 数据资源入表属于会计处理，不计入 NV。

|---|---|---|---|
| ctx | OSI/MetricFlow 风格的 YAML、verified queries（运行集 R 与评测集 E 物理分仓）、表卡片、术语表、skills、AGENTS.md、路由策略 | MetricFlow、dbt-mcp、sqlglot | 正确率、拒答率 |
| dsh-mcp | 受治理的数据入口（§4.2） | mcp 2.x / FastMCP 4〔E-7.20〕 | 权限合规、静默错误 |
| dsh-checks | 对账、不变量、PIT、基数、data-diff、价格有效期、实验质量；缺陷注入算子 | Pandera、GX Core、dbt tests | 捕获率、误拦率 |
| dsh-eval | golden set、结果集等价判分（含判分器自身校验）、pass^k、harness 适配、审查金丝雀 | Inspect AI〔E-7.21〕、MLflow 3.x | 回归、CPVC |
| dsh-gate | CI 策略步：三态判定，输出 in-toto Statement | actions/attest、cosign | 逃逸缺陷数 |
| dsh-value | 价值、成本、事故账本（数仓内约 20–30 个 dbt 模型） | 数仓、MLflow trace 中的成本 | NV、CPVC |

自建代码的目标是 ≤10k 行，硬上限 15k 行【假设】。

**明确不建**：对话 UI、NL2SQL 引擎、编排器、notebook、Catalog、模型注册表、沙箱运行时、LLM 网关、向量库或记忆库、证据数据库、多 agent 框架〔E-5.22〕。

状态只放在 git、数仓表和 MLflow 里。

### 3.4 部署剖面

**SMB / 本地优先**
- 组件：uv + Python 3.12 → dlt → DuckDB 1.5.x（暂不上 2.0）+ DuckLake 1.0 → dbt-core 1.12（1.13 目前仍是 beta）→ Pandera。
- 调度：cron 或 CI；确有需要时再用 Prefect 或 Dagster。
- 其他：单机 MLflow 3.x；MetricFlow 或 Cube；dsh-mcp 走 stdio。
- 沙箱：sandbox-runtime，必须配置 denyRead `~/.ssh`；或 Docker `network=none`。
- 注意事项：
  - 不要用 `pip install dbt`，它从 2026-09 起装的是专有的 Fusion 二进制〔E-7.2〕；
  - Cube 必须关掉 dev mode，否则会绕过认证〔E-7.14〕；
  - "本地优先"指数据不出公司环境，不是把数据拷到笔记本上。

**企业（已有数仓）**
- 数仓是 system of record：查询下推执行，以用户身份运行（OBO + RLS）。
- 跨引擎用 Iceberg 1.12 + REST catalog。
- 保留既有的 Airflow、DolphinScheduler 或 DataWorks 作为调度器。
- OpenLineage 事件写入现有 catalog，不用已停更的 Marquez〔E-7.22〕。
- MLflow 开启 RBAC。

**单平台企业**

如果原生 agent 加原生 MCP 已经覆盖了问数和编码（Genie MCP、BigQuery MCP 已 GA；dbt 远程 MCP 未见 GA 标注〔E-5.6, E-5.10, E-5.15〕），就**不建** dsh-mcp 的数据访问部分，只建 ctx、eval、gate 和账本，并在第 6 个月做平台替代测试。

**多平台企业**（例如境内 MaxCompute/DataWorks + 海外 Snowflake）

建一个薄的 dsh-mcp，只负责验证、证据、跨平台复算和答案证书。平台内的问数和编码交给各自的原生 agent，因为厂商 agent 主要围绕自家平台的资产和语义层工作（例如 BigQuery DE agent 只针对 BigQuery，Fabric data agent 最多 5 个源）〔E-5.10, E-5.13〕。

**实时 / 在线 ML**

v1 只做批量。实时模型（风控、定价、推荐）进入时，增加 G-online 门禁，要求：
- 在线/离线特征一致性；
- 特征新鲜度 SLA；
- 影子流量 ≥2 周；
- 金丝雀放量，违反 SLO 时自动回滚。

### 3.5 供应链与许可证

**许可证门禁**：用 SBOM + SPDX 标记以下许可证：ELv2（Soda Core v4）、BSL（lakeFS ≥1.87）、PLA（dbt Fusion 二进制）、AGPL、Proprietary。ELv2、PLA、AGPL 在企业内部使用通常没问题；lakeFS ≥1.87（BSL）只允许在内部生产中使用**未修改**的版本；对外托管或转售一律阻断〔E-7.2, E-7.7, E-7.8〕。

**避免使用**：

| 组件 | 原因 |
|---|---|
| Vanna、Daytona OSS | 已归档 |
| smolagents、AutoGen | 已停滞 |
| Marquez | 已停更 |
| CrewAI（核心路径） | 2026 年发了 289 个版本，变动过快 |

Polars 2.0、DuckDB 2.0、dbt v2 在自有数据上跑过回归之前不进生产〔E-7.2, E-7.10, E-7.11〕。避免清单的依据：Vanna〔E-7.16〕、Daytona〔E-6.21〕、smolagents/AutoGen/CrewAI〔E-7.19〕、Marquez〔E-7.22〕。

- 每季度做一次"工具投毒"和"描述注入"红队测试。

## 4. Agent 设计

### 4.1 拓扑：单写者 + 只读子 agent + 确定性骨架

这是 2026 年各家共同的结论。Cognition 的说法是"写操作单线程"〔E-6.16〕。Anthropic 的结论是：多 agent 适合广度阅读，但 token 约为普通对话的 15 倍（单 agent 约 4 倍），不适合紧耦合的编码〔E-6.15〕。需要扇出时，由脚本或调度器掌握计划〔E-6.17〕。

| 工作流 | 形态 | 写者 | 骨架 |
|---|---|---|---|
| W1 断修 | 构建或测试失败触发 → 只读分诊子 agent（读日志、契约 diff、血缘，返回 1–2k token 的摘要）→ 单写者在分支上写补丁 → CI → 干净上下文的 reviewer（只输出可执行探针）→ CODEOWNER 合并 | 1 | CI/DAG |
| W2 问数 | 单 agent，≤10 个工具；可以澄清、可以拒答；难写的 SQL 生成 N 个候选，按执行结果选 | 只写答案证书 | — |
| 富化 | 夜间脚本扇出只读 agent，输出用 JSON schema 校验，token 预算显式写明，产物交 steward 审 PR | 脚本 | 调度器 |
| W4 读数 | Skill + 确定性统计库；agent 只负责编排和写叙述 | 0 | — |
| W6 工厂 | 在现有编排器中跑确定性 DAG；agent 只写特征和候选**规格**；builder 看不到 holdout；scorer 用独立身份确定性运行 | 1 | DAG |

**禁用**：persona 团队；并行多写者；Supervisor 型架构（Databricks 已弃用 Supervisor API〔E-5.8〕）。

A2A 只用在组织或厂商的边界上〔E-6.5〕。

**W7 改为"假设工厂"**（L1）：产物是可证伪的假设，不是结论。这样既能用上当前 agent 最强的探索能力，又不让探索结果绕过证据阶梯。

- agent 在沙箱里用 `run_sql` 和 Python 自由探索，所有中间结果都是 T3。
- 最多输出 5 条假设，每条都必须附带一种证伪方式：
  - 一个能通过 `submit_answer` 对账的受治理指标查询（可升到 T1/T2）；
  - 或一份实验预注册草案（走 G5）。
- 没有证伪方式的假设不进入汇报。
- 由 DS owner 挑选要验证的假设。账本记录"假设被证实率"，低于 20%【假设】时，收紧该类问题的探索预算。
- 探索产生的 token 和仓库扫描费用，记入闲时配额（§2.3）。

### 4.2 dsh-mcp 工具面（每个角色 ≤10；参考实现全集 15 个，只读的上下文工具跨角色共享）

依据：OpenAI 的 data agent 把工具从约 40 个减到 13 个互不重叠的工具〔E-3.3〕；工具超过 30–50 个时，选择准确率明显下降〔E-6.14〕。参考实现里实际上线的工具面如下：

| 角色 | 工具 |
|---|---|
| analyst（7 个） | `list_metrics` `describe_metric` `query_metric` `search_catalog` `describe_table` `run_sql` `submit_answer` |
| data_scientist（10 个） | `list_metrics` `query_metric` `search_catalog` `describe_table` `run_sql` + `list_features` `propose_feature` `train_candidate` `request_final_evaluation` `request_release` |
| data_engineer（6 个） | `search_catalog` `describe_table` `run_sql` + `pipeline_status` `read_pipeline_file` `propose_pipeline_change` |

**设计要点**（均已在参考实现中落地）：

1. **受治理指标优先。** `query_metric` 走语义层，返回编译后的 SQL 和 `semantic_digest`。`run_sql` 只是探索用的：
   - 用 sqlglot 白名单，只允许单条 SELECT；
   - 禁止 bronze 和 PII 列；
   - 禁止 `read_csv`、`read_parquet` 这类文件函数，以及 ATTACH、COPY、SET；
   - 结果标为 uncertified。
2. **答案必须声明语义主张。** `submit_answer` 要求 agent 用 `metric_call` 说明自己答的是哪个指标、哪些维度、哪几个月。harness 把答案与受治理指标重新对账。这是捉住"自己写 SQL、数看起来合理但其实错了"的关键机制。没有主张的答案最多拿到 T3（探索），由人审。
3. **数据连接只读加锁。** DuckDB 设置 `enable_external_access=false` 和 `lock_configuration=true`，agent 无法读文件、联网或改配置。生产中对应的是：只读角色 + RLS + 仓库配额。
4. **custody 区不可达。** 没有任何工具能读真值、封存标签或世界生成器。
5. **工具从不向 agent 抛原始异常**，只返回 `{error, kind}`。每次调用都写入 `audit.jsonl`；预算耗尽时显式报错，不会被当成"完成"。

**协议**：MCP 2026-07-28，无状态、`tools/list` 顺序确定、长任务走 Tasks 扩展、`_meta` 里带 OTel traceparent〔E-6.1〕。

**认证**：OAuth 2.1 + RFC 9728/8707，令牌绑定 audience，禁止透传〔E-6.2〕。企业 IdP 用 EMA 接入〔E-6.3〕。钉钉、飞书能否作为 EMA 的 IdP 尚待核实；不能时由网关做 token exchange。

**防差分推断**：含 PI 的表只能通过固定维度的认证指标访问；小格做抑制（k≥10【假设】）；按 principal 审计查询之间的重叠。

### 4.3 Skills、AGENTS.md 与领域函数库

Skills 是跨厂商通行的过程封装格式。Claude Code、Codex、Gemini CLI、Genie Code、Cortex Code、TRAE、DeepSeek Deep Code 都支持；DataWorks 也支持自定义 SKILL.md〔E-6.6, E-5.20〕。

参考实现自带四个 skill：

| Skill | 要点 |
|---|---|
| `retention-uplift` | 只用随机化项目学 uplift（ITT）；离线验证策略；实验前算功效；按策略读数并计渠道成本；只凭本策略 PASS 的读数扩量 |
| `analytics-answer` | 先查语义层；任何治理数字都必须附 metric_call；探索结果标 uncertified |
| `churn-modeling` | 只用可信特征或已通过泄漏检查的提议特征；不看 holdout；价值只认实验读数 |
| `pipeline-breakfix` | 修复必须向后兼容；不许在同一个 PR 里改测试、对账或门禁；不许用独立记录校准自己 |

生产中再加：`schema-evolution`、`backfill-runbook`（只出计划和 dry-run diff）、`reconcile-before-claim`、`pit-features`、`experiment-design`、`ab-readout`（功效不足就输出 INCONCLUSIVE）、`uplift-targeting`、`model-card-and-pipia`。

每个 skill 的管理要求：
- 有一位领域 owner；
- 有版本号；
- 附 ≥10 个评测任务，改动后要跑回归。

**AGENTS.md** 写仓库约定。Claude Code、Codex、Gemini CLI 都会读它〔E-6.7〕。

**领域函数库**：离线由强模型对照 dev 标签蒸馏出带单测的函数，运行时由便宜模型编排。这是 DABstep 榜首的做法：用 Haiku 跑出 89.95，而同期 Claude Code + Opus 的基线是 66.93〔E-4.5〕。蒸馏时要留出数据，防止过拟合。

### 4.4 上下文层

**可信度排序**：
1. 语义定义
2. 认证表
3. verified queries（看板查询和 golden 排在临时查询之前）
4. 夜间富化生成的表卡片
5. 术语表和业务规则（配合澄清回合）
6. 事故与 caveat 库
7. 个性化

**规则**：

- **R/E 分离**：一条 verified query 要么用于运行时，要么用作评测真值，不能两用。Snowflake 的评测功能就是这样设计的〔E-3.19〕。参考实现的 `verified_queries.yaml` 有 14 条 context 和 6 条 eval，测试会检查两者不重叠。
- **不要把全部历史查询都建索引**：大多数查询是一次性的探索〔E-3.3〕；只检索历史 SQL 卡片的增益不显著〔E-4.12〕。
- **语义以可按需读取的文件提供**：把同样的知识塞进一个 24k 字符的 prompt，效果明显更差〔E-3.18〕。
- **用户纠错以 PR 形式进入 ctx 仓**，steward 在 2 个工作日内审核。不写入不透明的全局记忆，因为 NFRA 第 25 条点名了"记忆污染"〔E-2.15〕。
- **按血缘失效**：上游的 `pipeline_digest` 或 schema 一变，依赖它的 verified query、表卡片和 skill 就标为"待复验"，并移出运行集。这是上下文腐化的主要来源。
- **个性化**：默认优先用户近 90 天用过的表。Meta 的数据是 88% 的查询只用这类表〔E-3.10〕。这需要处理员工的查询日志，所以要做告知、限定用途、按 90 天滚动保留。

- **中文术语是语义层的一部分。**
  - 每个认证指标都要登记中文同义词和常见的口语叫法。
  - golden set 至少 50% 的题目，用业务方的中文原话。
  - 没有声明 metric_call 的答案能否被识别并对账，要在中文题上单独报告。
  - 参考实现目前只识别英文问法：同一个错误的"净收入"答案，英文提问会被 REJECT，中文提问只得到 T3/HOLD（不会被静默交付，但从"被拦下"退化成了"转人审"）。

### 4.5 模型路由与数据驻留

| 数据级别 | 可以进 prompt 的内容 | 中国 | EU | 美国/其他 |
|---|---|---|---|---|
| C0 元数据、schema、代码、合成数据 | 全部 | 已批准的模型；重要数据目录的元数据只走境内 | 已批准的模型 | 已批准的模型 |
| C1 内部聚合（小格抑制） | 聚合结果 | 境内优先 | EU 区域端点 | 签了 no-training 条款的端点 |
| C2 行级个人信息 | **不进 prompt**，只在沙箱里由代码处理 | 境内自托管，或已备案的境内 API | EU 区域 + ZDR + DPIA | ZDR |
| C3 敏感个人信息、重要数据、NFRA 高风险数据 | 只看 schema，访问需人工批准 | 只用自托管的开放权重模型 | 自托管，或 ZDR + DPIA | 自托管或专属部署 |

- **代码在数据旁边的沙箱里执行，原始行不出沙箱**：programmatic tool calling 可省 37% 的 token，code execution with MCP 的示例中省了 98.7%〔E-6.14〕。注意：Claude Managed Agents 和 programmatic tool calling 不在 ZDR 范围内，C2 及以上必须用自有的 loop〔E-6.10〕。
- **反向传输**：境内总部或 agent 查询海外的个人数据，构成 GDPR 第三国传输。二选一：
  - 签 SCC 并做传输影响评估（TIA）；
  - 个人数据分析留在区域内，只回传聚合结果。

  这一点需要法务确认。
- **模型分档**：

  | 档位 | 模型 | 用途 |
  |---|---|---|
  | 便宜档 | Haiku 5.5、deepseek-flash、GLM-5.3-Flash | 抽取、分类、SQL 草稿；目标承担 ≥60% 的调用【假设】 |
  | 默认档 | Sonnet 5.5、Qwen3.7-Max、DeepSeek V4-Pro、GLM-5.3 | 常规规划和编码 |
  | 前沿档 | — | 只用于离线蒸馏和疑难修复 |

  路由只为合规和成本服务，不是为了"更聪明"。OpenAI 的 data agent 就是单模型、没有路由器〔E-3.3〕。
- **供应商**：
  - 至少 3 家，其中 1 家境内、1 家可自托管；
  - 每个档位保留 2 个已批准的模型；
  - 设涨价告警。
- **中国控股实体的可得性**：中国控股企业（含其海外子公司）能否按合同使用 Anthropic、OpenAI，要由法务确认。因此**境内栈是默认执行器**，海外栈视合同而定。

### 4.6 Harness 可替换：契约在资产层，不在框架层

**可替换的契约**由以下部分组成：MCP 工具、SKILL.md、AGENTS.md、评测套件、答案证书的 JSON schema。

自运行 harness 的适配器只需要实现一个接口：`run(task, budget) → (transcript, artifacts, cost)`。

**可用的执行器**：
- `claude -p`：CI 中必须加 `--bare`，否则仓库里的 hooks 和 `.mcp.json` 会不经信任确认直接运行〔E-6.8〕；
- `codex exec`：OS 级沙箱，默认断网〔E-6.12〕；
- Qwen Code、OpenHands；
- Agents SDK、ADK、PydanticAI。

所有版本精确钉住。原因：Claude Code 发版非常频繁（2026-10-18 已到 v2.1.303）〔E-6.8〕；OpenAI Agents SDK 仍是 0.x〔E-6.11〕；第三方评测称 ADK 1.x 与 2.x 的存储格式不兼容〔E-6.13〕。

**封闭的平台 agent**（DataWorks Data Agent、CoWork、Genie Code）内部无法强制执行我们的 hooks。对策分四层：
1. 在同一套 golden set 上做黑盒评测；
2. 数据侧控制：只读角色、RLS、配额；
3. 输出侧门禁：答案证书、PR CI；
4. 平台自身的审批档位设为保守。

**节奏**：
- 模型、harness、skill、上下文、语义任何一个 pin 变更，都自动跑回归。
- 每季度做一次跨 harness 的全量对比（至少 2 个执行器，其中 1 个是境内的）。
- 每次大版本模型升级，做一次"拆脚手架"消融：每个 harness 组件都编码了某个会过期的假设〔E-6.18〕。

### 4.7 自治分级（自治是挣来的，不是配置出来的）

| 级 | 含义 |
|---|---|
| L0 | 只出计划或建议 |
| L1 | 只读执行并作答，带标签 |
| L2 | 写沙箱、分支或 dev；开 PR 或发布申请；由人合并 |
| L3 | 门禁全过后自动进入非生产，或自动发布到共享制品；事后抽审 |
| L4 | 在生产中自动执行有界、可逆的动作 |

| 工作流 | 起点 | 12 个月上限 | 升级条件【假设】 |
|---|---|---|---|
| 认证答案 → 提问者 | L1 | L1 | — |
| 认证答案 → 共享看板、周报 | L2 | L3 | 该任务类随机抽审 n≥150 且 0 错（上界约 2%），且 0 逃逸 |
| 董事会、对外、监管数字 | 人工 | 人工 | **永不升级**：T0 + 具名人签字 |
| DE 断修（不含契约变更） | L2 | L3（非生产自动合并） | 连续 50 个 PR 无大改合并、0 逃逸、reviewer 推翻率 <5%、回归 pass^3 ≥90% |
| 失败任务重跑 | L2 | L4（配额内、幂等） | 有幂等性证明，且连续 20 次无误 |
| 回填、契约变更、口径变更、模型晋级、触达客户 | L2 / 人工 | 不变 | **永不自动** |

**降级**：出现任何一次逃逸，自动降一级。

**依据**：
- 逐动作审批的部门，变革性成功率是 16%；充分使用 agent 的部门是 31%〔E-8.8〕。注意这是相关性数据。
- IMDA 的"关键检查点"做法〔E-2.22〕。

### 4.8 确定性护栏

**PreToolUse hooks**：
- 拒绝对 prod 的 DDL/DML；
- 拒绝读取 `custody/`、holdout 和世界生成器的源码；
- 拒绝把修复代码与测试、契约、门禁的改动放进同一个 PR；
- 超出预算记为 FAILED，不算完成。

**沙箱**：断网或只开白名单；输入只读挂载；短期凭据留在 harness 一侧，不进沙箱。

**数据内容一律视为不可信**：单元格、列名、工单文本里的指令不能改变权限。

**验证器或门禁宕机时**：写入、晋级、对外数字一律 fail-closed（HOLD）；只读探索答案 fail-open，但标为"未验证"。

## 5. 可信与验证：在没有完整金标准时建立可信度

### 5.1 oracle 目录：每种证据能证明什么、不能证明什么

| oracle | 能证明 | 不能证明 | 参考实现中的对应物 |
|---|---|---|---|
| **O1 独立记录对账**：财务关账、支付结算、源系统控制总数 | 加工过程正确 | 源系统对现实的记录是否正确；未关账期间不可用 | `reconcile:revenue_matches_finance_close`，逐月逐区精确到分 |
| **O2 不变量与变形关系**：守恒、声明为 m:1 的 JOIN 不增行、按事件身份去重、PIT、价格有效期 | 某一类错误不存在 | 口径本身是否正确 | `schema.yml` 测试、`verify/leakage.py` |
| **O3 双路径复算**：语义层 SQL 与 agent SQL 各算一遍；或转译到第二个引擎 | 实现层错误 | 两条路径共用了同一个错误定义 | `submit_answer` 对 agent 声明的 metric_call 重新对账 |
| **O4 golden set / verified query（E 集）** | 在已知问题上的能力 | 分布外的问题 | `verified_queries.yaml` 的 eval 分区 |
| **O5 延迟真值回溯评分**：答案连同快照存档，关账或标签成熟后自动重评 | 真实世界准确率，不需要人工标注 | 没有延迟真值的问题 | 封存评估使用成熟后的 6 月流失标签 |
| **O6 已知抽样概率的随机抽检** | 无偏的错误率估计 | —（错误发现队列不能拿来估错误率） | — |
| **O7 随机实验** | 因果效果 | 实验人群之外 | `decision/experiment.py` + 一次性 oracle |
| **O8 缺陷注入与审查金丝雀** | 检查本身的召回率 | 真实准确率 | 世界生成器的 D1–D9 + `bench` 中的 naive 变体 |

**规则**

1. **对账独立性。** 独立记录不得出现在被核对指标的上游血缘里。否则，一个"用财务表校准收入"的修复会因为构造方式而必然通过对账。参考实现用 `pipeline.oracle_independence` 检查强制这一点，基准里也专门放了这个陷阱。
2. **未关账期间最高到 T1**，并标注"暂定，关账后回溯评分"。
3. **非财务指标**：先找源系统的控制总数当 O1。找不到的，封顶 T1/T2，靠随机抽检兜底。
4. **因果结论只认随机化。** 准实验的结论标为 ASSUMPTION-DEPENDENT，并配反驳和敏感性分析（DoWhy）。
5. **金标本身也要审计。** 公开基准的答案键在部分子集上错误率达 53–63%（BIRD Mini-Dev 52.8%，Spider 2.0-Snow 62.8%）〔E-4.2, E-4.18〕，自建的 golden set 也会有错。做法是 LLM 审计员加双人审，kappa ≥0.8。
6. **判分器本身也要校验。** 执行结果匹配有假阳和假阴〔E-4.14〕。每季度人工复核 100 条判分，判分器错误率 ≤2% 才能用于门禁【假设】。

### 5.2 一条证据阶梯，一套用户标签

**内部证据阶梯（产物级）**

| 级 | 内容 |
|---|---|
| V0 | 能执行（不算证据） |
| V1 | 契约、类型、测试；SQL 静态检查；答案能被重新执行复现 |
| V2 | 不变量、PIT、变形关系 |
| V3-D | 独立路径复算一致 |
| V3-R | 与独立记录精确对账，严格强于 V3-D |
| V4 | 封存 holdout、成熟标签或回溯评分，由独立身份的 scorer 执行 |
| V5 | 预注册的随机实验（ITT、SRM、功效） |

**用户信任标签**（阶梯在用户侧的投影）

| 标签 | 条件 | 允许用途 |
|---|---|---|
| **T0 已对账** | V3-R：已关账，与独立记录精确一致，或差异都已解释 | 对外、监管、董事会，另需具名人签字 |
| **T1 受治理-暂定** | 走认证指标路径 + READY 构建 + V2 + 配置评测通过 | 内部 KPI 和看板，标"暂定"，到期回溯评分 |
| **T2 已交叉核验** | 非认证问题，V3-D 双路一致 + V2 | 内部决策支持 |
| **T3 探索** | 仅 V1，并列出假设 | 只能用于探索，禁止进入 KPI 或汇报 |

模型和因果声明不另设标签，用 V4/V5 加结论状态表达：VERIFIED / INCONCLUSIVE / NOT_VERIFIED_CAUSAL。

### 5.3 评测（eval 是 harness 的门禁，不是事后报告）

**题源**
- 来自真实日志、工单和 IM 登记。
- 起步用 20–50 个真实失败〔E-6.20〕；90 天达到 150–200 题，其中 20% 是越界或歧义题；6 个月达到 300–500 题。
- 每题配 2–4 种改写，允许多个可接受答案。LinkedIn 约 60% 的题有多个正确答案〔E-3.7〕。

**判分**
- 比较执行结果集是否等价，不比较 SQL 字符串。
- 分组件评分：意图、选表、能否执行、结果是否正确（Uber 的 decoupled 模式〔E-3.5〕）。

**报告指标**
- pass@1 和 pass^3。单次 75% 的成功率，pass^3 只有约 42%〔E-6.20〕。
- 静默错误率：答错，且既没拒答，也没降级标签。
- 拒答的精确率和召回率、CPVC、p95 延迟、人工介入次数。

**样本量纪律**
- 0 错时，错误率的 95% 上界约为 3/n：n=150 时为 2.0%，n=300 时为 1.0%。
- 200 题在 85% 附近的置信区间约 ±4.9pp。
- 要分辨"静默错误从 10% 降到 5%"，非配对时每臂约需 430 道独立题目。
- 回归用配对 McNemar 检验，不用固定阈值。

**版本化**
- 每道题绑定 `metric_definition_digest`。口径一变，相关题目标为 stale。
- R 集和 E 集物理分仓，CI 做哈希检查。

**厂商自报数字一律不采信**，必须在自有题集上复测。例如：Genie Code 77.1%、Cortex Sense 83%、Quick BI 98%〔E-5.5, E-5.17, E-3.16〕。

### 5.4 门禁

| stage | 必需证据 | 审批 |
|---|---|---|
| `project_intake`（建议，参考实现未实现） | 决策记录 + 基线 + 功效预检（≤3 个月可达功效 ≥0.8）+ 理论上限下单位经济为正 + 随机化授权 | business owner + DS/统计 owner |
| `answer_publish` | SQL 静态检查、重执行一致、与受治理指标对账；**答案主张须与问题一致**（指标、月份、筛选、分组），不一致就转人审 | — |
| `pipeline_merge` | 克隆环境构建并跑测试（含对账）；对旧快照做回归 diff（必须完全一致）；**对账独立性**；测试削弱检测；锁定参考数据 | CODEOWNER（参考实现中由仓库分支保护在 harness 之外强制：gate ALLOW 表示 CI 证据齐全，不等于合并许可） |
| `feature_accept` | 时间穿越检查 + 静态时间检查 | — |
| `model_shadow` | 封存评估 + 候选级泄漏证据 | — |
| `model_experiment`（G5） | 作用于**策略**：策略所用模型已放行（policy.models）+ 在历史随机化项目上的离线 Qini 与价值验证（policy.offline_qini）；预注册与功效计算在实验设计步完成 | business owner |
| `model_scale`（G6） | 同上 + 实验读数 PASS（扣除成本后 LCB95 >0）+ SRM 通过 | business owner + risk |
| `retrain_promote` | 封存评估 + 候选级泄漏证据 + champion/challenger 对比 | risk |

**判定语义**（参考实现 `evidence/gate.py`，64 个测试）：

- 只计入"主体 digest 匹配、检查项必需、生产者已授权"的证据。未授权或主体不匹配的证据**被忽略**，不会导致 REJECT。请求者自己产出的证据也被忽略。
- ERROR 后重试得到的 PASS 可以 supersede 前者。
- **FAIL 一旦出现就保持，直到被显式 supersede。** 换一个产物就是新的主体，不允许"重试到绿"。
- 缺失、过期、ERROR、INCONCLUSIVE 一律判 HOLD，并说明需要什么证据才能解除。
- 未知 stage 或格式错误的策略判 REJECT（配置错误不等于放行）。
- 审批禁止自审，同一个人跨角色只计一次。
- **HOLD 率**健康区间为 5–15%，超过 20% 触发绕过告警。EY 调查中有 47% 的企业承认绕过过治理〔E-2.24〕。

**生产化**
- 证据输出为 in-toto Statement，由 CI 的 OIDC 身份签名：GitHub 上用 `actions/attest`，国内自建 GitLab 用 cosign + KMS。
- 本地 JSONL 证据标为 UNSIGNED-LOCAL，在 prod 阶段一律视为 HOLD。
- 参考实现附了一个 CI 样例：`.github/workflows/dsh-gate.example.yml`。

**全局 holdout**
- G6 扩量后，保留 5–10% 的合格人群作长期对照，至少保留 2 个季度。
- 用它测效果衰减和反馈回路：用被干预过的数据重训，会产生自我强化的偏差。

### 5.4.1 非干预型模型的证据路径

适用于需求预测、异常检测、用于排产或备货的评分等模型。这类模型多数无法按个体随机化。如果套用 G6 的规则，它们会永远停在 HOLD。

| 环节 | 要求 |
|---|---|
| 评估 | 滚动起点回测，封存最近 ≥2 个完整周期作 holdout；同时报告相对季节性朴素基线的提升（如 MASE <1），并按 SKU、门店、区域切片 |
| 价值 | 决策成本回放：把新旧预测分别输入同一套补货或排班规则，用实际需求算缺货、积压、加班成本。结果标为"回放估计"，取各窗口 95% 下界再乘 κ=0.3，在账本中单列为 ③b，不与实验证明的 ③ 合并汇报 |
| 因果 | 能做时，用 switchback（按周轮换）或按门店、区域做整群随机化；通过后才计入 ③ |
| 门禁 | `model_shadow` 改为影子运行 ≥4 周，加延迟真值回溯评分（O5）；`retrain_promote` 用 champion/challenger 在同一回测窗口上做配对比较 |
| 局限 | 回放假设需求不受决策影响。存在删失需求或价格变动时，这个假设不成立，必须写进 caveats |

### 5.5 人工复核：抽样、分级、看证据包而不是 transcript

**100% 人审**：对外数字、生产写入、模型晋级、新增 verified query、契约或口径变更、回填、高风险场景。

**抽样审**：认证答案随机抽 5%，低置信度和新领域的答案全审。每条都人审会重新造成瓶颈，这是 Ramp 的教训〔E-3.13〕。

**审查金丝雀**
- 往复核队列里注入 2–5% 的已知缺陷。
- 审查者检出率低于 80% 时，暂停其审批权并重新培训。
- 不到 10 秒完成的审批视为橡皮图章【假设】（防橡皮图章的要求见〔E-2.22〕）。

**每个产物都有具名负责人。** 只有一个人时，不宣称做了双人复核。

### 5.6 统计检查清单（内置在 A/B 读数 skill 与 G5/G6 门禁中）

- **预注册**：随机化单位、人群、主指标、MDE、功效、周期、停止规则。
- **SRM**：χ² 检验 p<0.001，即判实验无效。
- **主分析**：用 ITT，按随机化单位计算 cluster-robust 标准误。
- **切片**：做多重比较校正。
- **HTE**：要么预先指定，要么标为探索性。
- **功效不足**：输出 INCONCLUSIVE，并给出所需样本量。

**这条规则在合成世界里有直接对应**【实测】：两个策略各分一半人群时，完美 uplift 名单每组只有约 113–141 人，"扣除成本后价值 LCB95 > 0"的通过概率约 0.18–0.24，"流失下降"的 ITT 检验约 0.53–0.64；即使把整月 500 个名额都给完美名单（每组 250 人），价值检验的功效也只有约 0.37（ITT 约 0.87）。系统必须如实输出 INCONCLUSIVE，不能把"流失少了几个人"包装成"显著有效"。

## 6. 交付、组织与采纳

### 6.1 三种交付单位

| 交付物 | 载体 | 门禁 | 回滚 |
|---|---|---|---|
| 问数答案 | IM 线程或 BI，附**答案证书** | `answer_publish` | 口径变更后召回 |
| 管道、语义、上下文、skill、门禁本身 | **PR** | `pipeline_merge` | git revert，从上一个 digest 重建；表用 time travel 或快照恢复 |
| 回填 | 计划 PR：范围、成本、dry-run diff | 双人审批 | 快照恢复 |
| 模型 | 候选 + 封存评估证据 | `model_shadow` → G5 → G6 | 回退整份 release manifest（模型、预处理、阈值、策略、镜像）；schema 不兼容时切到规则兜底 |
| 决策 | 决策记录（问题、选项、证据 tier、owner、预期效果、复查日期）+ 实验 | G6 | 停止实验，回退策略 |
| harness 变更（模型、harness、skill、语义、prompt） | PR | 全量回归评测 | 回退 pin |

**答案证书**包含：
- 问题，以及术语解析（净额还是毛额、是否排除测试账号）；
- metric_id 及其 digest；SQL 及其 digest；
- 构建快照、检查与对账状态、tier、caveats；
- 模型和 harness 版本、成本。

发往企业外部的证书要加 AI 生成标识〔E-2.10, E-2.2〕。

**报告与看板的交付规则**

- 报告（周报、分析备忘录、汇报材料）由正文加证书清单组成。正文里的每个数字都要带证书编号。CI 检查是否有不带编号的数字；只要有一个，整份报告降为 T3。
- 报告的标签取正文中最低的那一个，不取平均。
- 正文用了"导致""因为""带来"这类因果措辞，但没有 V5 证据时，改写为相关性表述，并加 caveat。
- 看板的每个图块绑定一条 R 集 verified query，按血缘失效规则同步标注"待复验"（§4.4）。
- 业务读者看到的交付物格式见附录 A。

### 6.2 CI、环境与身份

**身份分四类**：

| 身份 | 权限 |
|---|---|
| agent | 只有 dev 写权限，可以开 PR |
| CI/gate | 跑检查、签名、部署 |
| 封存 scorer | 独立身份 |
| prod 凭据 | 只在受保护环境里释放。GitHub 最多可设 6 名必需审批人，并可禁止自审〔E-1.10〕 |

**CI 顺序**：

sqlglot 解析和 lint → 在克隆环境构建 → 契约和测试 → 对账 → data-diff → 血缘影响分析与对账独立性断言 → 评测回归 → 签名证明 → gate → 受保护环境

凡是改动 agent 配置文件（`.mcp.json`、hooks、AGENTS.md、skills）的 PR，都需要 owner 审批。

### 6.4 采纳与变更管理

- **嵌入现有渠道**：
  - 入口放在钉钉、飞书、企微、Slack 和 BI 里。LinkedIn 把 SQL Bot 嵌进 DARWIN 后，使用量提升 5–10 倍〔E-3.7〕。
  - 用"agent 优先 + 人工升级 SLA"取代原来的数据求助群。
- **用分批随机上线测效果**：
  - 按团队分 3–4 批，批次顺序随机（stepped-wedge）；
  - 用带时间固定效应的混合模型估计分流量和周期时间；
  - 用这个估计取代自报的"省了几小时"。
- **周会与记分卡**：
  - 每周 30 分钟，把纠错整理成 verified query。
  - 每月公布记分卡：自助解决率（与审计正确率配对）、pass^3、抽审上界、CPVC、HOLD 率、事故。
- **培训 2 小时**：
  - 怎么读标签和证书；
  - 什么时候不该信：超出能力前沿时，人的正确率会从 84.5% 跌到 60–70.6%〔E-8.12〕。
- **定位是增强，不是替代**：
  - Gartner 调查（350 名高管）：试点自主能力的组织中，约 80% 裁了员，却没有相应的 ROI 提升〔E-8.7〕。
  - AI 暴露职业里 22–25 岁员工的就业比趋势低 19%，主要原因是少招人〔E-2.23〕。
  - 要给初级分析师留出转向 steward、评测、复核岗位的路径。
- **厂商驻场工程（FDE）合同**：写明 IP 归属、知识转移和退出方案。Gartner 预测到 2028 年，70% 的企业会放弃由厂商 FDE 构建的 agentic AI〔E-8.7〕。

### 7.2 转化为设计要求

1. **用例入口强制做风险分级登记。** 信贷、核保、雇佣、教育、基本服务以及 NFRA 高风险清单内的场景，一律标为 HIGH-RISK，触发重控制：可解释模型、逐笔理由码、人工最终决策、偏差测试。
2. **数据最小化。** prompt 里只放元数据和聚合结果；行级 PI 只在沙箱里由代码处理（§4.5）。
3. **按数据级别和法域做模型路由。** 中国 PI 只用境内模型；EU 数据走区域端点 + ZDR，不只依赖 DPF。
4. **不可篡改的审计日志。** 记录 prompt 和响应、工具调用、生成的代码、访问过的表和列、审批人、决策输出。保存期限：EU ≥6 个月；PIPIA 和 Colorado 3 年；NFRA 要求保留推理路径。
5. **审批检查点放在编排层，不放在 prompt 里。** 需要审批的情况：访问敏感数据前、跨境前、写生产前、模型晋级前、输出进入重大决策前。监测推翻率，防止橡皮图章；保留 kill switch 和人工兜底。
6. **合规文档作为流水线产物自动生成。** 包括模型卡、数据表（datasheet）、PIPIA/DPIA 草稿和审计导出，把合规变成证据的副产品，而不是另一套流程。
7. **外发内容加 AI 标识**（中国标识办法、EU Art.50）。
8. **agent 安全**（对应 NFRA 第 25 条和 NIST agent 安全工作）：
   - 每个 agent 用独立的最小权限身份；
   - 工具白名单，默认只读；
   - 按租户隔离记忆；
   - 把数据内容当作不可信输入；
   - 出站白名单。
9. **协调删除权与可复现性**（PIPL 第 47 条、GDPR 第 17 条）：
   - 证据、证书、审计日志里只存摘要、聚合结果和 digest，不存行级个人信息。
   - 含个人信息的快照设保留期，默认不超过 13 个月【假设】；超期后只保留去标识的版本。
   - 收到删除请求时，依次执行：在源表打墓碑 → 重建受影响的快照 → 回归 diff 改为按"预期差异清单"对账，不再要求完全一致。
   - 封存 holdout 和全局 holdout 在删除后重算样本量；样本量跌破预注册下限时，相关结论降为 INCONCLUSIVE。
   - 审计日志中必须保留的部分做假名化，密钥单独保管，到期后销毁密钥（crypto-shredding）。

## 9. 参考实现 dsharness：它是什么，实测到了什么

### 9.1 定位与结构

dsharness 是本方案的**测量仪器**，不是生产平台。它用一家合成的订阅制公司来做实验：这家公司 21 个月里约有 7,600 名客户，每个数字都有保存在 custody 区的已知真值；源数据里埋了 9 类真实世界常见的缺陷（D1–D9），还有一个 2026-03 至 06 的随机化挽留项目。

在这个世界里，它实现了本方案中需要自建的部分：

| 方案组件 | 参考实现 | 生产中替换为 |
|---|---|---|
| 源契约与受治理管道（§3.2） | Pandera 契约、dbt 风格的 SQL 模型和数据测试、与财务关账逐分对账、登记事故的限定范围修正、按有效期核对价格表 | dbt / SQLMesh / DataWorks |
| 语义层与上下文（§4.4） | YAML 语义模型（11 个指标起步，含挽留项目的 ITT 指标）、带 PII 和时间语义标签的目录、verified queries（运行集与评测集分离） | MetricFlow / Cube / 平台语义视图 |
| dsh-mcp 与 skills（§4.2–4.3） | 三个角色，每个 ≤10 个工具；审计和预算；MCP 2.x stdio 服务；3+1 个 SKILL.md；AGENTS.md；`.mcp.json` | 远程 MCP + EMA，接入网关 |
| 验证库（§5.1） | SQL 静态检查、答案对账、时间穿越泄漏检查与静态时间检查、bootstrap、SRM、校准 | 同左，接入企业 CI |
| 门禁与证据（§5.4） | 三态门禁（修复了草稿的 bug）、审批禁止自审、in-toto Statement 导出（UNSIGNED-LOCAL） | CI OIDC 签名 + 受保护环境 |
| ML 工厂（§3.2） | 时点正确的特征、声明式训练模板、封存评估（每个任务 3 次预算）、uplift 学习（只用 ITT）与离线 Qini | 平台 ML / MLflow |
| 决策闭环（§5.6） | 策略注册、预注册实验设计、一次性 oracle（每位客户每月只能进一个实验）、按策略读数、渠道经济学 | 实验平台 |
| 评测（§5.3） | 脚本化基准（真值只来自评估方），以及一个可接真实 agent 的运行器（pass@k / pass^k / 每个正确答案的成本） | Inspect AI / MLflow eval |

代码规模：`src/` 约 1.2 万行 Python，其中世界模拟器、基准和演示约占四分之一（约 3,200 行）；测试约 5,500 行，共 444 个测试。生产中真正需要自建的部分符合 §3.3 的规模目标。

### 9.2 运行方式

### 9.4 脚本化基准（`dsh bench`，全尺寸世界，38 项）【实测】

基准里有两类脚本 agent：careful 走正确路径；naive 的每个变体都植入一种真实世界常见的错误，并且总是自称成功。真值只来自评估方：custody 真值表、封存标签、oracle。

| 范围 | 项数 | 正确 | 错误 | **无 harness 的静默失败** | **有 harness 的静默失败** | 被拦下（REJECT·FLAGGED / HOLD） | 正确但未自动交付 |
|---|---|---|---|---|---|---|---|
| 全部 | 38 | 10 | 28 | **28** | **0** | 28（27 / 1） | 3（2 项转人审，1 项按设计 HOLD） |
| 问数 | 25 | 6 | 19 | 19 | 0 | 19 | 1（CSAT 没有受治理指标 → T3，转人审） |
| DE | 5 | 1 | 4 | 4 | 0 | 4 | 0 |
| ML | 4 | 1 | 3 | 3 | 0 | 3 | 0 |
| 决策 | 4 | 2 | 2 | 2 | 0 | 2 | 2 |

**各类错误被哪项检查拦下**：

| 错误类型 | 拦下它的检查 |
|---|---|
| 裸 SQL、按外观去重、漏掉测试账号、忽略退款、主张与数字不符 | `answer.reconcile`（与受治理指标对账） |
| 只适配 v2 的修复 | `pipeline.regression_diff`（旧快照被破坏） |
| ÷100 修复 | `pipeline.ci_build`（价格表测试）+ 回归 diff |
| 用财务表"校准"收入 | `pipeline.oracle_independence` + 回归 diff。评估方还构造了一个探针：删掉 5 条东区 7 月收费，这个管道照样判 READY |
| 删除对账测试 | CI 构建（测试被删）+ 独立性检查 |
| 三种泄漏特征（自报 dev AUC 0.948，封存真值约 0.67） | `model.leakage` |
| "风险 × LTV"价值主张 | 缺少实验读数 → HOLD |
| 电话渠道扩量 | `policy.offline_qini` FAIL → REJECT |

**有一项 naive 结果"碰巧正确"**：per-protocol 分析声称 −12 分/人，真值 +109，误差落在 300 分的容差内。评估方判它"正确"，harness 仍然 HOLD 它，因为方法不成立、也没有实验读数。基准把这类情况单列，不计为 harness 的失败。

**这些数字能说明什么、不能说明什么**：

- 它们证明的是**机制覆盖**：每一类被植入的错误，都由预期的那项检查拦下；代价是一部分正确但无法自动核验的答案要转人审。
- 它们不是 LLM agent 的错误率。脚本 agent 不是随机样本。要比较"静默错误率从 10% 降到 5%"，每臂约需 430 道独立题（§5.3）。
- 真实 agent 的测试用 `dsh live` 运行，需要已登录的 Claude Code，也可以通过 `--command-template` 接入其他 CLI。本机的嵌套 `claude -p` 当前显示 "Not logged in"，所以真实 agent 的数字**尚未测量**。

### 9.5 决策价值：实测得到的四条经济规律【实测】

1. **能否学出 uplift，取决于数据采集。** 在世界 v2a 中，价格敏感度只能从工单和加购行为里弱弱地观测到：学到的 uplift 与真值的 Spearman 相关约 −0.01，离线检查直接 FAIL，策略被 REJECT。2026-01 起，产品分析开始埋点"定价页浏览"（v2b），同样的流程得到 +0.36，前 30% 覆盖了 oracle 的 54%。**决定能挣多少的，往往是"采集了什么"，而不是"用了什么模型"。**这也是采集阶段需要 agent 参与的原因：提出埋点与数据契约 PR（§3.2）。
2. **价值 = 风险 × 可说服性。** 只按"价格敏感"选人，会选中一批本来就不会走的人，结果亏钱。在这个世界里，把定价页浏览量作为单因子规则选人，前 500 人每月 −¥182。效应要放在 logit 尺度上、再用效应修饰因子建模，风险和可说服性才会自然相乘。
3. **一个月的实验分辨不出每人几毛钱的差异。** 按真值，uplift 策略是 +0.78 元/人，风险策略是 −1.69 元/人。但单月实验（风险策略每组约 250 人，uplift 策略每组约 105 人）的 95% CI 半宽约 ±10–21 元/人；就算模型完美，单月拿到 PASS 的概率也只有约 18–37%。所以正确做法是：两个策略都判 INCONCLUSIVE，继续有界实验（G5），不扩量（G6），并报告 MDE 以及是否值得继续加样本。**这种诚实本身就是价值：naive 声称 +19.84 元/人，如果按它扩量，风险策略每联系一个人实际亏 1.69 元。**
4. **规模决定可行性。** 把世界放大到 4 倍（7 月约 1.43 万名在册客户）做探索性运行（配置与结果见 `research/scale_4x.md`）：同样的方法学到的 uplift 策略**按真值为正**，每月约 +¥1,500–3,400，具体取决于选人规则，约为同规模 oracle 的 13–30%；而真值风险排序（假设能完美预测流失）还要更好。但单人价值仍然只有几元，要拿到确定结论，仍需多月或更大的实验。这和 §2.4 的盈亏点结论一致：**中小企业做 uplift 建模往往不划算。更现实的做法是：用领域假设定一个简单策略，再做足量、长期的实验；或者把有限的预算用在"不做亏钱的事"上。**

### 9.6 对抗审查：发现了什么、修了什么

方案要求"验证器自己也要被验证"，参考实现也照此执行了一轮。以下几路审查各自独立进行，每个漏洞都由另一个 agent 独立复现确认后才修复：

- 两组红队：一组攻击问数，一组攻击管道、模型和决策；
- 一次逐行代码审查；
- 一次文档事实核查；
- 一次需求完整性审查。

| 编号 | 严重度 | 问题 | 修复 |
|---|---|---|---|
| RT-AN-01 | 严重 | **主张替换**：agent 声明的 metric_call 可以与问题不一致——问 2 月却答 3 月，问东区却答北区，问"按区域"却给一个总数。数字与声明的主张对得上，于是拿到 VERIFIED / T0 / ALLOW。原检查只发警告，而警告不进入证据 | 新增 `claim_contradictions`：只解析**问题**本身（不看 agent 的附加说明），检查指标、月份包含关系、筛选值和分组维度。不一致时对账判 INCONCLUSIVE，结果降为 T3 / HOLD 转人审。15 组已审核的问题/主张对不受影响 |
| DSH-CORR-001 | 严重 | **custody 外泄**：数据工程 agent 提交的管道 SQL 里，用"CTE 名与文件路径同名"骗过静态筛查，在 CI 构建时读出 custody 真值和任意本地文件，并通过测试失败样例回传 | 纵深防御：①构建在 bronze 落表后立即关闭外部访问并锁定配置，runner 拒绝在未加锁的连接上运行；②静态筛查改为按作用域解析 CTE，解析失败即拒绝；③拒绝系统目录表 |
| DSH-CORR-002 | 中 | 问数 SQL 的静态检查有同样的 CTE 作用域漏洞，可以读系统目录（表名、列名、文件路径） | 同上，共用一套解析逻辑 |
| DE-2 | 高 | 回归 diff 只比对一个已发布快照。一个修复如果只篡改**之后月份**的用量或工单数据，也能拿到 ALLOW | 新数据快照上，凡是基线管道能构建的 silver 表，也必须完全一致 |
| ML-1 | 中 | 封存评估的出错信息里带有从 holdout 推导出的计数，而且不扣预算 | 先用构建自身的人群检查覆盖率；凡是读过 custody 的返回一律扣预算，出错信息中不含任何数字 |

**教训**：
- 两个严重漏洞都不是"模型不够聪明"造成的，而是 **harness 自身的边界条件**。
- 静态筛查必须有不依赖它的第二道防线（执行层禁止访问文件）。
- 主张与问题的一致性，本身也是需要验证的对象。

这印证了 §5.1 的规则：每一层防线都要假设上一层会漏。

**文档事实核查**：共找出 38 处引用不当、数字口径不一致或说法过强的地方，已逐条更正。例如 §2.7 的实验功效，原文用的是 ITT 功效，并不是门禁实际要求的价值功效。

**完整性审查**：找出 10 处缺口，已补入 §2.4.1、§3.2、§4.1、§4.4、§5.4、§5.4.1、§6.1、§7.2、§8.0 和附录 A。

**仍未覆盖的**：红队有两条线（问数和 DE/ML）中途被安全分类器打断，并没有试完所有计划的攻击向量。建议每次大版本发布时，用 `dsh bench` 加专门的红队任务重新跑一轮。

## 10. 风险与证伪

### 10.1 主要风险

| 风险 | 早期信号 | 缓解 |
|---|---|---|
| **没人策展**（最可能的失败方式） | 纠错 PR 积压超过 2 周；verified query 停止增长 | steward 由业务方出资，作为域准入前提；空缺 >60 天即冻结该域 |
| 验证成本超过节省 | CPVC 上升，复核排队 | 抽样、分级、证据包、金丝雀 |
| 语义定义本身是错的 | 门禁只能验证"与定义一致" | O1 对账 + 口径委员会 + owner 签字 |
| 平台吞掉这一层（Cortex AI Gateway、Databricks 收购 Quotient、dbt Agents Schema） | 单平台企业中，原生能力追平本层 | 保持本层足够薄，资产放在 git；做平台替代测试 |
| 评测泄漏或 Goodhart | 离线分数高，审计错误率也高 | R/E 分仓、隐藏种子、季度轮换；自助率与正确率配对报告 |
| 橡皮图章审批或绕过治理 | 审批 <10 秒、推翻率接近 0、HOLD 率 >20% | 审查金丝雀；让受治理路径成为最快的路径 |
| 境内 token 涨价、限流、中断；海外供应商不可用 | 涨价告警 | 多供应商、自托管兜底、闲时调度、境内栈为默认 |
| 数据内容中的提示注入或越权 | 注入指令被执行 >0 次 | 在工具层做授权、沙箱、出站白名单、不透传令牌 |
| 厂商产品改名或弃用 | Databricks Knowledge Assistant 9 个月内从 GA 变成 legacy〔E-5.8〕 | 只在 MCP、SQL、OSI 等协议层集成 |
| 合成世界过拟合 | 基准分数好看，真实切片差 | 90 天内跑真实切片；缺陷分布用真实事故校准 |
| 仓库扫描成本失控 | agent SQL 成本占比上升 | dry-run 估算、配额、分区 lint |

### 10.2 什么结果会证明本方案错了

以下各条都在试点中实测：

1. **语义优先不成立。** 在本组织的 golden set 上，"语义层 + MCP"相对"裸 SQL"的提升 <8pp → 改为只买原生对话问数。
2. **验证层不值这个成本。** 真实试点抽审中，加上检查与门禁后静默错误率下降不到 20% → 退回到只做上下文。
3. **标签没有区分度。** 随机抽检中 T1 的错误率不低于 T3 → 重做标签体系。
4. **工具面不必自建。** 平台原生 agent 加其自带的 eval，与本方案相差 <3pp 且更便宜 → 不建 dsh-mcp，只保留资产、评测和账本。
5. **省工时的价值论证不成立。** 实测 κ <0.2，且 6 个月内没有业务方愿意做随机化 → 价值论证只剩外部支出替代，模型工厂停在离线阶段。
6. **"单写者、不用评审团"过于保守。** 评审团或投票在同等预算下使静默错误率相对下降 ≥30%、成本 ≤1.5 倍，且在真实数据上复现 → 修订这一立场。
7. **SMB 部署不成立。** 稳态策展需要 >2 FTE/域。
8. **中国 PI 场景要收缩。** 境内 harness 落后 >10pp，补上下文也追不回来 → 中国 PI 场景收缩到 C0/C1 任务。
